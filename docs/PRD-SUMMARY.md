# Statement Bridge - product summary

What the extension is for and how it is put together, distilled from the
original design notes for anyone extending it.

## The problem

Turning a bank statement (a CSV export, or a PDF, scanned or not) into clean
rows in a spreadsheet is repetitive and fiddly: every bank's export has a
different header, date format, sign convention, and layout. Statement Bridge
does that mapping once per statement type ("Meridian Bank savings, CSV",
say) and then recognizes every later statement from the same source
automatically.

## The 30-second monthly path

The full setup (column mapping, checks, currency, date range) happens once
per statement type. Every month after that, the goal is: drag files in,
watch them process, click "Copy for Sheets". Detail is always one click
away but never in the way.

**Home (the fast path)**
1. Drop zone at the top; collapses to a slim bar once files exist.
2. One row per file: a progress bar resolves to a status line, e.g.
   "Meridian Bank savings, ****4821, 1 to 31 Aug 2026, 42 rows, All checks
   pass." A healthy file needs nothing else.
3. Attention cards appear only when something needs a decision, each with
   the one action that resolves it: a new statement type ("Map this
   statement"), a layout change ("Update mapping" / "Use anyway"), low
   confidence ("Looks like Riverside Bank 360, is that right?"), rows with
   warnings ("3 rows need a look"), a missing exchange rate, or duplicates
   merged (informational, with Undo).
4. An export panel at the bottom once at least one file is healthy: one
   summary line (preset, date range, row count, currency mode), a primary
   "Copy for Sheets" and secondary "Download CSV". Only real blockers (an
   unmapped statement type, a missing rate, zero rows in range) disable
   copying; warnings are shown next to the button instead. A "Change" link
   expands an inline drawer for date range, currency mode, export preset,
   and per-account included/excluded counts, without leaving the page.
5. Defaults are remembered between sessions: last preset, date-range choice,
   currency mode, saved rates.

**Confirm-first setup for a new bank statement**: one question per screen -
does the extracted table look right, and if not, which of a short list is
wrong (dates, amounts/sign, missing or extra rows, something else) - each
leading straight to the one relevant step, rather than a generic wizard.

**Simple mode** (the default for a non-technical user): almost none of the
above vocabulary is visible up front. A drop area, a plain per-file status
line ("Reading page 2 of 3", "Done, 31 transactions"), a big "Your
transactions are ready" result card with the two export buttons, and quiet
links to the fuller controls one level down. Every control that exists
still exists, just not by default.

## How statement types work

A "statement type" (called a profile internally) is stored as JSON: which
bank/account it is, whether the source is CSV, PDF or XLSX, the signatures
used to recognize it again (header text, preamble keywords, PDF anchor
phrases, filename pattern), how to parse it (header row, delimiter, column
positions for a PDF), a source-column-to-standard-field mapping, the date
format, number format, and sign convention (signed / debit-credit columns /
CR-DR markers / positive-is-out, etc.). See `docs/PROFILE-SCHEMA.md` if you
want the exact shape; `src/core/profiles.js` is the source of truth.

A handful of starter statement types ship in
`src/core/builtin-profiles.js`, built against fictional example banks
(Meridian Bank, Harbour Card, Riverside Bank, Summit Bank, Anchor Bank,
Lattice Bank, Northwind Bank) so the repository never ships a real bank's
name or layout as a default. They exist to demonstrate the parsing
capabilities (grouped PDF layout detection, tabbed CSV parsing, CR/DR
markers, debit/credit column pairs) a real bank's export is likely to need.
Every real bank statement type is created (or adjusted) by the user, once,
through the wizard.

## Adding a new bank

Nothing in the extension needs a code change to support a new bank: drop a
statement, walk the wizard once (it pre-fills a guess from the file), save.
If you are contributing a new *capability* the parser doesn't have yet
(a layout shape none of the built-ins cover), add a synthetic fixture under
`extension/test/fixtures/` (generated by a script under
`extension/test/fixtures/gen/` where practical) named after a fictional
bank, a builtin profile in `extension/src/core/builtin-profiles.js`, and a
regression test. Never name a real bank in a fixture, a builtin profile, or
test data - see `CONTRIBUTING.md`.

## Privacy model

Everything runs on-device: no network requests, no host permissions,
`connect-src 'none'` in the extension's CSP. A dropped statement is parsed
in the browser (CSV/PDF text) or recognized on-device (Tesseract.js, for a
scanned PDF); nothing is ever uploaded. See the top-level `README.md`'s
"privacy promise" for the short version.
