# EXPORT-AND-DUPES progress log

## Part 1: duplicates and CSV flags (agent A)

- Rule 1: `normalize.js` keys off `version.csv` (the CSV/XLSX path; a PDF profile leaves it undefined) and filters `CONFIDENCE_FLAGS` (low_confidence_ocr, sign_unclear, unknown_currency, balance_mismatch) plus amount_alt/low_confidence_hint off every CSV row; `pipeline.js` runs `tagBalanceMismatches` for a PDF entry only. unparseable_date/missing_amount/pending/date_outside_period still apply. 5 unit tests (one per suppressed flag, one for the true failures) in normalize.test.js, 1 in pipeline.test.js.
- Rule 2: the within-file possible_duplicate fingerprint in `normalize.js` now runs only for a non-CSV source, so two identical rows in one CSV are two real transactions. Test: CSV not flagged, the same records read as a PDF still flagged.
- Rule 3: `dedupe.js` gained `isSameStatement` (same statementType AND the same date range) - only then does `mergeAcrossFiles` still merge a cross-file overlap. Every other overlap keeps both rows and returns one `pairs` entry per fingerprint per file pair. The range test is equality, not overlap: a June file next to a June-July file overlaps but is NOT a re-download, and rule 5's first run expects exactly that case to be asked about. home.js passes `profile.statementType` + `dateRangeOfRows(rows)` per file. 7 new dedupe tests; the 4 existing merge tests now carry the same-statement identity.
- Rule 4: `checks.js` FLAG_LABELS gained `duplicate_across_files: "Looks like the same transaction in two files"`. home.js renders one card per pair (`renderDuplicatePairsBanner`/`renderDuplicatePairCard`) showing both rows side by side with each file's name (and the page snippet for a PDF row), with Keep both / Keep one. Keep both remembers the pair key so it is never asked again; Keep one drops the losing row (dedupe.js's CSV-over-OCR winner) into the existing "N rows merged / Undo" notice, so a hand-merge is still undoable. Default focus: Keep both for CSV+CSV, Keep one when either side is a PDF; focus is taken once per pair and never out of a focused input. Reused the existing decision-card CSS (workspace.css is agent B's file).
- Rule 5: `dups` scenario in dev/e2e-extension.mjs, two runs, 14 checks, all green; screenshot audit/fix-shots/dups-1440.png, read. Deviation: the spec's "two different-type CSVs" second run is unreachable in the real app - the dedupe fingerprint is scoped to the account label, which carries the statement type, so a savings row and a credit-card row never match. Run 2 answers the reachable form (same account, different ranges) with Keep both and asserts the count is unchanged.
